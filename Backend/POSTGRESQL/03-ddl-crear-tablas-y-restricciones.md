# 03 — DDL: CREAR TABLAS Y RESTRICCIONES

> **DDL** (*Data Definition Language*) son las sentencias que definen la
> **estructura**: `CREATE`, `ALTER`, `DROP`. Las **restricciones** (*constraints*)
> son reglas que la base de datos **obliga a cumplir siempre**, venga el dato de
> donde venga (psql, tu API, pgAdmin...). Son tu **última línea de defensa**.

---

## 3.1 `CREATE TABLE`: la sintaxis

```sql
CREATE TABLE nombre_tabla (
    columna1 TIPO [restricciones],
    columna2 TIPO [restricciones],
    ...
    [restricciones de tabla]
);
```

**Puntos clave:**
- Columnas separadas por **comas**; la **última no** lleva coma.
- Termina en `;`.
- Nombres en `snake_case`, tablas normalmente en **plural** (`socios`, `clases`).
- Si la tabla tiene FK, la tabla a la que apunta debe **existir antes**.

### Ejemplo REAL copiado (`Proyecto-SQL/Proyecto-SQL/gimnasio.sql`)

```sql
--B1.1
CREATE TABLE planes (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nombre VARCHAR(50) UNIQUE NOT NULL,
    precio_mensual NUMERIC(6,2) NOT NULL CHECK (precio_mensual >= 0)
);

--B1.2
CREATE TABLE socios (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    dni VARCHAR(9) UNIQUE NOT NULL,
    nombre VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE NOT NULL,
    fecha_alta DATE NOT NULL,
    plan_id INTEGER NOT NULL REFERENCES planes(id)
);
```

**Desglose de una columna:**

```
precio_mensual  NUMERIC(6,2)  NOT NULL  CHECK (precio_mensual >= 0)
└─── nombre ──┘ └── tipo ───┘ └────────── restricciones ──────────┘
```

## 3.2 Claves primarias autogeneradas

```sql
id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

| Parte | Significado |
|-------|-------------|
| `INTEGER` | Es un número entero |
| `GENERATED ALWAYS AS IDENTITY` | Postgres lo **genera** (1, 2, 3...) y **no te deja** ponerlo a mano |
| `PRIMARY KEY` | Única + no nula + crea un índice automáticamente |

### Formas que verás por Internet

```sql
-- ✅ Moderna y estándar (la que usas en todos tus proyectos)
id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY

-- Permite poner el id a mano si quieres
id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY

-- 🕰️ Antigua (propia de Postgres, sigue funcionando)
id SERIAL PRIMARY KEY
```

> 📌 Como el `id` se genera solo, en los `INSERT` **no se pone**. Mira tus inserts:
> `INSERT INTO planes (nombre, precio_mensual)` → no aparece `id`.

## 3.3 Las restricciones, una a una

### `NOT NULL` — obligatorio

```sql
nombre VARCHAR(100) NOT NULL,   -- obligatorio
telefono VARCHAR(15),            -- opcional (admite NULL)
```

**Ejemplo REAL (`gimnasio.sql`, B1.4):**

```sql
CREATE TABLE monitores (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    dni VARCHAR(9) UNIQUE NOT NULL,
    nombre VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE NOT NULL,
    telefono VARCHAR(15),
    especialidad VARCHAR(50)
);
```

> 📌 `telefono` y `especialidad` no llevan `NOT NULL` → por eso en el B2.4 puedes
> insertar monitores **sin** ellos.

### `UNIQUE` — sin repetidos

```sql
email VARCHAR(150) UNIQUE NOT NULL,
```

#### UNIQUE de **varias columnas** (la pareja no se repite)

**Ejemplo REAL (`gimnasio.sql`, B1.6 y B1.8):**

```sql
CREATE TABLE reservas (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    socio_id INTEGER NOT NULL REFERENCES socios(id),
    clase_id INTEGER NOT NULL REFERENCES clases(id),
    fecha_reserva DATE NOT NULL,
    UNIQUE (socio_id, clase_id)
);

CREATE TABLE monitor_especialidades (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    monitor_id INTEGER NOT NULL REFERENCES monitores(id),
    especialidad_id INTEGER NOT NULL REFERENCES especialidades(id),
    CONSTRAINT uk_monitor_especialidad UNIQUE (monitor_id, especialidad_id)
);
```

```
UNIQUE (socio_id, clase_id)
   (1, 1) ✅
   (1, 3) ✅   ← mismo socio, otra clase: vale
   (2, 1) ✅   ← otro socio, misma clase: vale
   (1, 1) ❌   ← la PAREJA repetida: error
```

> 📌 **Restricción de columna vs de tabla:** `UNIQUE` al lado de una columna solo
> afecta a esa columna. Si afecta a **varias**, se escribe **al final** como
> restricción de **tabla**.
> 📌 `CONSTRAINT uk_monitor_especialidad` le pone **nombre** a la restricción. Así
> el mensaje de error es más claro y luego puedes borrarla con `ALTER TABLE ... DROP CONSTRAINT uk_monitor_especialidad`.
> Si no la nombras, Postgres inventa uno (tipo `reservas_socio_id_clase_id_key`).

### `CHECK` — condición que siempre se cumple

**Ejemplo REAL (`gimnasio.sql`):**

```sql
precio_mensual NUMERIC(6,2) NOT NULL CHECK (precio_mensual >= 0)
plazas INTEGER NOT NULL CHECK (plazas > 0),
```

**Ejemplo REAL (`puta/api-books-nest/database/schema.sql`):**

```sql
  pages INTEGER NOT NULL CHECK (pages > 0),            -- la base de datos también valida
```

```sql
  role VARCHAR(20) NOT NULL DEFAULT 'customer'
    CHECK (role IN ('customer', 'employee'))  -- solo estos dos roles
```

> 📌 El comentario de tu `schema.sql` lo dice todo: *"la base de datos **también**
> valida"*. En tu API ya validas con DTOs (`class-validator`), pero si alguien mete
> datos por `psql` o hay un bug, el `CHECK` lo frena igualmente.

### `DEFAULT` — valor si no te lo dan

**Ejemplo REAL (`schema.sql`):**

```sql
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()        -- fecha de creación automática
```

```sql
  role VARCHAR(20) NOT NULL DEFAULT 'customer'
```

Por eso, en el `INSERT` de libros no aparece `created_at`:

```sql
INSERT INTO books (title, author, pages)
VALUES
  ('Cien años de soledad', 'Gabriel García Márquez', 471),
  ...
```

y en `users.service.ts` se crea un usuario solo con `email` y `password_hash` → el
`role` queda en `'customer'` automáticamente.

Otros `DEFAULT` útiles (ejemplo propio):

```sql
activa BOOLEAN NOT NULL DEFAULT TRUE,
fecha_alta DATE NOT NULL DEFAULT CURRENT_DATE,
id UUID PRIMARY KEY DEFAULT gen_random_uuid()
```

### `REFERENCES` — clave ajena

**Ejemplo REAL (`gimnasio.sql`, B1.3 y B1.5):**

```sql
CREATE TABLE tarjetas (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    codigo VARCHAR(20) UNIQUE NOT NULL,
    activa BOOLEAN NOT NULL,
    socio_id INTEGER UNIQUE NOT NULL REFERENCES socios(id)
);

CREATE TABLE clases (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    fecha_hora TIMESTAMP NOT NULL,
    sala VARCHAR(50) NOT NULL,
    plazas INTEGER NOT NULL CHECK (plazas > 0),
    monitor_id INTEGER NOT NULL REFERENCES monitores(id)
);
```

**Forma larga equivalente** (restricción de tabla, con nombre):

```sql
monitor_id INTEGER NOT NULL,
CONSTRAINT fk_clases_monitor FOREIGN KEY (monitor_id) REFERENCES monitores(id)
```

## 3.4 ¿Qué pasa al borrar el "padre"? `ON DELETE`

Por defecto, Postgres **no te deja** borrar una fila si otra tabla la referencia.
Puedes cambiar ese comportamiento (no se usa en tus proyectos; ejemplo propio):

```sql
socio_id INTEGER NOT NULL REFERENCES socios(id) ON DELETE CASCADE
```

| Opción | Al borrar el socio... |
|--------|-----------------------|
| *(nada)* / `NO ACTION` / `RESTRICT` | ❌ Error si tiene reservas (lo que pasa en tu gimnasio) |
| `CASCADE` | 🧹 Borra también **sus reservas** |
| `SET NULL` | Pone `socio_id = NULL` en sus reservas (la columna debe admitir NULL) |
| `SET DEFAULT` | Pone el valor por defecto |

> ⚠️ `CASCADE` es cómodo pero **peligroso**: un `DELETE` puede borrar en cadena
> media base de datos. Úsalo cuando el hijo **no tenga sentido** sin el padre
> (reservas de un socio, líneas de un pedido...).

## 3.5 Las restricciones en acción: los errores de tu B3

Lo más valioso de tu `gimnasio.sql` es el bloque **B3**: inserts hechos **a
propósito** para que fallen.

### Ejemplo REAL copiado (`gimnasio.sql` + `respuestas.md`)

```sql
-- B3.1  plan_id = 99 no existe
INSERT INTO socios (dni, nombre, email, fecha_alta, plan_id)
VALUES ('99999999Z', 'Nora Prueba', 'nora@gym.com', '2026-10-27', 99);
```
> Línea del error (traducida): "Violación de restricción de clave foránea". La clave foránea plan_id REFERENCES planes(id) lo ha impedido

```sql
-- B3.2  email de Ana repetido
INSERT INTO socios (dni, nombre, email, fecha_alta, plan_id)
VALUES ('99999999Z', 'Nora Prueba', 'ana@gym.com', '2026-10-27', 1);
```
> Línea del error (traducida): "Violación de restricción UNIQUE en la columna email". La restricción UNIQUE en email lo ha impedido

```sql
-- B3.3  segunda tarjeta para Ana (socio_id 1)
INSERT INTO tarjetas (codigo, activa, socio_id)
VALUES ('TJ-0099', TRUE, 1);
```
> "Violación de restricción UNIQUE en la columna socio_id"

```sql
-- B3.4  Ana reserva otra vez la clase 1
INSERT INTO reservas (socio_id, clase_id, fecha_reserva)
VALUES (1, 1, '2026-10-30');
```
> "Violación de restricción UNIQUE en las columnas socio_id, clase_id"

```sql
-- B3.6  borrar un plan que usan socios  ❌
DELETE FROM planes WHERE nombre = 'Básico';

-- B3.7  borrar un plan que no usa nadie  ✅
DELETE FROM planes WHERE nombre = 'Mañanas';
```
> **B3.8: B3.6 falla y B3.7 funciona. Los dos son planes. ¿Por qué?**
> Porque B3.6 intenta borrar un plan que sí tiene socios asociados. B3.7 borra un plan que no tiene ningún socio, por lo que no hay referencias que lo protejan.

### Cómo leer el error real de Postgres

```
ERROR:  insert or update on table "socios" violates foreign key constraint "socios_plan_id_fkey"
DETAIL:  Key (plan_id)=(99) is not present in table "planes".
```

```
ERROR:  duplicate key value violates unique constraint "socios_email_key"
DETAIL:  Key (email)=(ana@gym.com) already exists.
```

```
ERROR:  new row for relation "planes" violates check constraint "planes_precio_mensual_check"
```

| Mensaje | Restricción | Código SQLSTATE |
|---------|-------------|-----------------|
| `violates foreign key constraint` | FK | `23503` |
| `duplicate key value violates unique constraint` | UNIQUE / PK | `23505` |
| `violates check constraint` | CHECK | `23514` |
| `null value in column ... violates not-null constraint` | NOT NULL | `23502` |

> 📌 Esos **códigos** (`23505`...) los recibirás en tu API como `error.code` cuando
> uses `pg`. Sirven para responder un `409 Conflict` cuando un email ya existe, por
> ejemplo.

## 3.6 `ALTER TABLE`: cambiar una tabla que ya existe

No aparece en tus proyectos. Ejemplos propios sobre el gimnasio:

```sql
-- Añadir una columna
ALTER TABLE socios ADD COLUMN telefono VARCHAR(15);

-- Añadir una columna obligatoria con valor por defecto (las filas existentes lo reciben)
ALTER TABLE tarjetas ADD COLUMN creada_en TIMESTAMPTZ NOT NULL DEFAULT NOW();

-- Borrar una columna
ALTER TABLE monitores DROP COLUMN especialidad;

-- Renombrar columna / tabla
ALTER TABLE socios RENAME COLUMN nombre TO nombre_completo;
ALTER TABLE socios RENAME TO clientes;

-- Cambiar el tipo
ALTER TABLE socios ALTER COLUMN email TYPE VARCHAR(255);

-- Poner / quitar NOT NULL
ALTER TABLE monitores ALTER COLUMN telefono SET NOT NULL;
ALTER TABLE monitores ALTER COLUMN telefono DROP NOT NULL;

-- Poner / quitar DEFAULT
ALTER TABLE tarjetas ALTER COLUMN activa SET DEFAULT TRUE;

-- Añadir / quitar restricciones con nombre
ALTER TABLE clases ADD CONSTRAINT ck_plazas_max CHECK (plazas <= 50);
ALTER TABLE monitor_especialidades DROP CONSTRAINT uk_monitor_especialidad;
```

> ⚠️ `ADD COLUMN ... NOT NULL` **sin** `DEFAULT` falla si la tabla ya tiene filas
> (¿qué valor les pondría?). Pon un `DEFAULT` o añádela como opcional y rellénala
> después con un `UPDATE`.

> 📌 Tu observación de A5 cuadra aquí: la tabla `monitores` tiene una columna
> `especialidad VARCHAR(50)` **y** además una tabla N:M `monitor_especialidades`. La
> columna sobra (y solo permitiría una especialidad por monitor) → candidata a
> `DROP COLUMN`.

## 3.7 `DROP` y `TRUNCATE`

```sql
DROP TABLE reservas;                 -- borra la tabla (estructura + datos)
DROP TABLE IF EXISTS reservas;       -- sin error si no existe
DROP TABLE socios CASCADE;           -- ⚠️ borra también las FK que apuntan a ella

TRUNCATE TABLE reservas;             -- vacía la tabla, la estructura se queda
TRUNCATE TABLE reservas RESTART IDENTITY;  -- y reinicia el contador del id a 1
```

| Comando | ¿Borra datos? | ¿Borra la tabla? | ¿Admite `WHERE`? |
|---------|---------------|------------------|------------------|
| `DELETE FROM t` | ✅ | ❌ | ✅ |
| `TRUNCATE t` | ✅ (todos, muy rápido) | ❌ | ❌ |
| `DROP TABLE t` | ✅ | ✅ | ❌ |

### Orden al borrar tablas

Al revés que al crear: **primero los hijos**, luego los padres.

```sql
-- Script "reset" típico para empezar de cero (ejemplo propio)
DROP TABLE IF EXISTS monitor_especialidades;
DROP TABLE IF EXISTS especialidades;
DROP TABLE IF EXISTS reservas;
DROP TABLE IF EXISTS clases;
DROP TABLE IF EXISTS monitores;
DROP TABLE IF EXISTS tarjetas;
DROP TABLE IF EXISTS socios;
DROP TABLE IF EXISTS planes;
```

> 📌 Si pones esto **al principio** de un `.sql`, puedes ejecutarlo tantas veces
> como quieras sin errores de "la tabla ya existe". Alternativa al crear:
> `CREATE TABLE IF NOT EXISTS planes (...)`.

## 3.9 Errores comunes con DDL

| Error | Causa | Solución |
|-------|-------|----------|
| `relation "planes" does not exist` | Creas `socios` antes que `planes` | Respeta el orden padre → hijo |
| `relation "planes" already exists` | Ejecutas el script dos veces | `DROP TABLE IF EXISTS` / `CREATE TABLE IF NOT EXISTS` |
| `syntax error at or near ")"` | Coma después de la última columna | Quita la última coma |
| `cannot insert a non-DEFAULT value into column "id"` | Pones el `id` a mano con `GENERATED ALWAYS` | No incluyas `id` en el `INSERT` |
| `cannot drop table socios because other objects depend on it` | Hay FK apuntándola | Borra antes los hijos (o `CASCADE`, con cuidado) |

```sql
-- ❌ Coma final
CREATE TABLE planes (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL,
);

-- ✅
CREATE TABLE planes (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL
);
```

## ✅ Resumen rápido

1. `CREATE TABLE nombre ( columna TIPO restricciones, ... );`
2. PK moderna: `id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY`.
3. `NOT NULL` obligatorio · `UNIQUE` sin repetidos · `CHECK (cond)` regla · `DEFAULT valor` · `REFERENCES tabla(id)` FK.
4. `UNIQUE (a, b)` al final de la tabla = la **pareja** no se repite.
5. `CONSTRAINT nombre ...` para dar nombre a las restricciones.
6. `ON DELETE CASCADE / SET NULL` cambia qué pasa al borrar el padre.
7. `ALTER TABLE ... ADD/DROP/RENAME/ALTER COLUMN` para modificar.
8. `DROP` borra la tabla; `TRUNCATE` la vacía; `DELETE` borra filas con `WHERE`.
9. Crear: padres → hijos. Borrar: hijos → padres.
